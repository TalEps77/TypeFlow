7.1-1 — why PARTIAL (two reasons). The implementation is not WhisperKit-backed. The AC specifies “a WhisperKit EnergyVAD-backed implementation”. 7.2-2 — the significant finding of this audit. The accuracy half of the criterion is met and evidenced: commit f2d826c records that the previous nil strategy silently dropped a chunk around the 30 s mark while .vad did not. The speed half was not met. The same commit records 6.42 s with chunking vs 6.29 s without on a 71.7 s clip — marginally slower — and states plainly that parallelizing “isn’t the main win here”. The story is marked done against an AC reading “completes measurably faster”, and that admission appears nowhere in epics.md: not in the AC, and not in the “Known limitations (as delivered — documented, not fixed)” block at epics.md:1040-1043, which is exactly where the project’s own convention says it belongs. Nothing was falsified — the number is in the git record — but the epic reads as though the latency goal was achieved. The real delivered win was completeness, not wall-clock.

7.2-3 / 7.2-4 — why PARTIAL rather than UNVERIFIABLE. Both have concrete manual evidence in f2d826c (an 8 s clip byte-identical at 1.23 s vs 1.19 s; ~345 MB RSS), so they are not unverifiable — they are verified once, by hand, against a narrow sample. Two caveats: the short-recording guarantee rests entirely on a vendored-dependency branch (isChunkable) that no app test pins, and the memory figure was taken on a ~3-chunk clip while maxRecordingDuration (AppState.swift:117, SettingsView.swift:856) permits 300 s — roughly 11 chunks — against an unbounded worker default of 16.

Honesty of the documented “known limitations” — accurate but over-broad. The ~1 s tail-drop and per-chunk language detection under Auto are real and correctly disclosed rather than quietly fixed. One overstatement: the tail-drop is stated unconditionally, but VADAudioChunker.chunkAll only skips the tail when a VAD split lands inside the final windowPadding; when startIndex + maxChunkLength >= seekClipEnd the last chunk runs to the true end.

Open-by-decision items — inertness audit

The brief was to confirm these are safely inert rather than to demand fixes. One holds. One does not.

Update checker — genuinely inert, and pinned. updatesEnabled is a nonisolated static let false (UpdateChecker.swift:65), so every branch is compile-time constant. It gates the only two network entry points: checkOnLaunchIfNeeded() (:152 — which has no production caller at all; the sole reference outside the file is UpdateCheckerTests.swift:38) and checkForUpdates() (:164). The ungated checkForUpdates(releaseProvider:) (:176) makes no network call and has no production caller. There is no timer, no periodic poll, no launch hook. The Settings button is removed rather than disabled (SettingsView.swift:1096) and is the only writer of showingUpdateSheet (:1063, :1103, :1197), so UpdateView — and with it downloadUpdate/openDMG — is unreachable. The menu-bar banner check (MenuBarView.swift:90) is belt-and-braces over an activeUpdateInfo only that path could set. Three tests pin it (UpdateCheckerTests.swift:16, :24, :35). No bypass found. No fix demanded.

Homebrew — inert from the app, NOT inert from CI. The cask files are fine: nothing in the running app reads them (UpdateChecker.detectHomebrewInstall only probes local Caskroom receipts at :104-131, reachable only through the disabled flow), and both carry explicit ⚠️ UNPUBLISHABLE AS-IS markers (homebrew/Casks/vocamac.rb:7-12, vocamac-nightly.rb:1-4).

But there is a fifth workflow the AC never enumerated and the prior review did not count: .github/workflows/update-homebrew-cask.yml. Verified directly this session. On release: [published] (:5-7) it:

  1. builds DMG_URL="https://github.com/jatinkrmalik/vocamac/releases/download/v${VERSION}/TypeFlow-${VERSION}-arm64.dmg" — upstream’s repo, for a filename upstream has never published (:27);
  2. runs curl -sL -o vocamac.dmg "$DMG_URL" — no -f, no exit check — so the 404 body is written to the file (:28);
  3. shasums that 404 body (:34);
  4. checks out jatinkrmalik/homebrew-vocamac with secrets.HOMEBREW_TAP_TOKEN and commits the bogus version and checksum into the public tap (:37-67).

This is reachable from a release tag, mutates a third-party public repository, and carries no unpublishable marker. “Not reachable from the running app” is true and insufficient. Inertness does not hold here — reported because the premise fails, not to re-litigate the decision to leave the cask urls pointing upstream. The narrowest containment consistent with the existing decision is to gate the workflow off (or add if: false) alongside the cask markers, until the fork has a release repo.

Bottom line

Neither epic contains a violated acceptance criterion, and nothing was found to be falsely claimed as delivered. Twenty-two of thirty-five live criteria are fully satisfied with code and test citations; the twelve PARTIALs are mostly acceptance-text that drifted behind better code, plus a handful of genuinely thin spots.

Story 7.3’s cut is recorded honestly on all three axes that matter: no abandoned streaming code exists anywhere in Sources/ or Tests/, the implementation-phase criteria are explicitly marked not-delivered rather than quietly claimed, and the deferred concurrency protection is named as still deferred rather than folded into the lock deletion. Two secondary artifacts — architecture.md:437 and RETROSPECTIVE.md:44 — still describe the deleted lock as present and should be reconciled with the epic and tracker, which are correct.

Epic 8’s thirteen prior-review fixes are all still present, with no regressions. Its PARTIALs are almost entirely at the edges the original sweep did not reach: release.sh, the fifth workflow, the two docs/ files, the About tab’s links, and the README badge block.

Four things stand out as worth acting on, in rough order of consequence:

  1. update-homebrew-cask.yml is not inert. A published release curls a nonexistent DMG from upstream with no error check and pushes the resulting checksum into a public third-party tap. The open-by-decision framing covered the cask files; it did not cover this workflow, which nobody enumerated.
  2. Story 7.2’s speed criterion was not met. The story is marked done against “completes measurably faster” while its own commit f2d826c records 6.42 s vs 6.29 s and says parallelizing “isn’t the main win here”. The work was worth shipping — it fixed a real chunk-dropping bug — but the epic should say what was actually delivered.
  3. testSelectedModelSizeDefault asserts a default the code does not have. It fails in isolation and passes in the suite only on state another test leaks. Tracked as merely “order-dependent”, which understates it.
  4. VG-8: .vad chunking converted a hard transcription failure into a silently dropped chunk. A long dictation can lose a 30-second block, the app reports success, and text with a hole in it is injected. This is a behavior change introduced by story 7.2 that no acceptance criterion covers and no test detects.

The Command Mode route is the most consistently under-verified surface across both epics: its language resolution (VG-5), its glossary gate (VG-5b), and its abort-path cleanup (AF-17) are each a duplicated copy of dictation logic whose dictation twin is tested and whose Command Mode twin is not.
